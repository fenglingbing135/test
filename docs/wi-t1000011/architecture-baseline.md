# 系统设计

<!-- system-design: scope -->
## 1. 整体方案与设计基线

### 1.1 技术栈与运行形态

| 关注点 | 结论 |
| --- | --- |
| 服务端 | Node.js ≥ 20，ESM JavaScript，入口 `src/server.js`，HTTP 框架 Hono |
| 前端 | React 18 + TypeScript + Vite，构建产物由同一 Hono 进程托管 |
| UI 组件 | Ant Design 5（`antd`、`@ant-design/icons`） |
| 存储 | 服务端本地文件存储（每份审核一条记录目录），不使用数据库 |
| 任务执行 | 进程内异步任务队列（并发 1），审核状态持久化在记录上 |
| 外部集成 | 代码托管平台 REST（GitHub / GitLab 适配器）、OpenAI 兼容对话补全接口 |
| 运行 | 单进程本机 Web 应用；`PORT` 默认 `8787`，`DATA_DIR` 默认 `./data` |

前后端同源部署：`/api/*` 为 JSON 接口，其余路径返回 SPA。开发期 Vite 开发服务器将 `/api` 代理到本机服务端，业务状态只有服务端一处权威，浏览器不持久化审核数据、凭证或设置。

### 1.2 责任划分

- 服务端拥有审核记录、审核状态、问题清单与平台凭证的唯一权威；前端只做展示与交互，不本地推断审核结果。
- 审核在请求返回后异步执行：发起接口只负责校验输入、拉取变更（链接方式）、落记录并入队，随后由队列推进「进行中 → 成功/失败」。
- 变更内容（diff 文本）随记录持久化，用于重新发起审核与结果页展示代码片段；不依赖浏览器会话。

### 1.3 全局 UI 基线

| 维度 | 结论 |
| --- | --- |
| 应用/业务模板 | 开发者审核工作台（单用户、无登录） |
| 展示模板 | `split-master-detail` |
| 视觉风格 | Modern SaaS：中性浅色工作区、深色左侧导航、单一主色 + 高/中/低状态色、细边界、少阴影 |
| 组件体系 | Ant Design 5 + `@ant-design/icons`，代码片段使用等宽字体块 |
| 应用壳 | 左侧导航（新建审核 / 审核历史 / 平台设置）+ 顶部上下文栏（当前记录来源与状态）+ 主工作区 |
| 主工作流布局 | 审核历史为左侧记录列表 + 右侧记录详情；新建审核在详情区以「粘贴变更 / MR 链接」双模式表单呈现，提交后直接进入该记录详情 |
| 目标设备 | 桌面 Web（默认 1280px 及以上）；需求未要求移动端或窄屏，不设计窄屏专属布局 |
| 长内容处理 | 代码片段与问题说明在卡片内限高并提供展开/收起；文件路径超长时以悬停标题展示完整路径 |

依据：需求以「逐条查看问题清单、按级别筛选、按文件聚合、回看历史记录」为核心动作（AC-03、AC-05），记录列表与结果详情需要并列协同，故选择 `split-master-detail`，而不是输入/结果并列的生成器布局。

关键全局状态（均需在界面上可区分）：

- 列表加载中：骨架屏占位；列表为空：说明「暂无审核记录」并引导发起审核。
- 审核进行中：状态标识 + 结果区展示进行态，前端定时刷新该记录状态，无需用户手动刷新。
- 审核失败：展示失败原因文本与「重新发起」入口，失败记录保留在列表中。
- 拉取失败：在新建审核表单内就地提示具体失败原因，不创建记录、不跳转。
- 未发现问题：结果区明确展示「未发现问题」，与失败、进行中区分。
- 凭证未配置：MR 链接方式提交时就地提示需先完成平台凭证配置，并提供前往设置的入口。

### 1.4 可重复验证方式

验收涉及外部异步事件（审核状态推进）与非确定性输出（模型结果），按受影响场景约定可重复验证方式：

- 审核引擎支持 `REVIEW_ENGINE=stub` 确定性实现：按固定规则从 diff 解析文件与行号并生成固定级别的问题条目，不访问外部模型；供 AC-01、AC-03、AC-04、AC-05 的自动化与界面验证使用。生产默认值为 `live`。
- `REVIEW_STEP_DELAY_MS`（毫秒，仅测试环境设置）让队列在状态切换之间停留，使「进行中」状态可被观察和断言；不设置时按正常速度执行。
- 平台拉取同样支持 `PLATFORM_FETCH_MODE=stub`：按链接返回固定 diff 或按测试需要返回 `unauthorized` / `not-found` / `network` 失败，用于 AC-02 的正常与异常分支。
- 以上开关只从服务端环境变量读取，仅用于本次验收；正常运行不改变产品行为，也不在界面暴露任何测试入口。
- 恢复初态：验证脚本使用独立临时 `DATA_DIR` 与空闲端口，结束后删除临时目录，不影响本机数据。

| `src/server/store/reviews.js` | 审核记录的目录型文件存储、原子写、列表投影、删除 | 审核记录唯一权威 |
| `src/server/store/settings.js` | 平台凭证文件存储、写入权限控制、脱敏读出 | 平台凭证唯一权威 |

### 2.3 接口摘要

字段级定义、错误码与 ID 约定见 `docs/wi-t1000011/technical-contract.md`。

| 方法 | 路径 | 用途 | 方向 |
| --- | --- | --- | --- |
| GET | `/api/health` | 服务存活检查 | 前端 → 服务端 |
| GET | `/api/settings/platform` | 读取平台凭证配置（令牌脱敏） | 前端 → 服务端 |
| PUT | `/api/settings/platform` | 保存平台类型、实例地址、访问令牌 | 前端 → 服务端 |
| DELETE | `/api/settings/platform` | 清除平台凭证配置 | 前端 → 服务端 |
| GET | `/api/reviews` | 审核记录列表（摘要投影，含状态与问题数量） | 前端 → 服务端 |
| POST | `/api/reviews` | 创建审核：粘贴变更或 MR 链接；成功返回记录并异步审核 | 前端 → 服务端 |
| GET | `/api/reviews/:reviewId` | 记录详情：状态、失败原因、整体结论、问题清单 | 前端 → 服务端 |
| POST | `/api/reviews/:reviewId/retry` | 对同一记录重新发起审核 | 前端 → 服务端 |
| DELETE | `/api/reviews/:reviewId` | 删除记录 | 前端 → 服务端 |

调用方向：浏览器 → Hono 路由 → 仓储/队列/引擎 → 代码托管平台与模型服务。路由不直接访问文件系统之外的存储细节，平台与模型调用只经由适配器与客户端，便于替换实现与注入测试实现。

## 3. 数据与持久化

### 3.1 目录布局

```text
data/                       # DATA_DIR，默认 ./data，启动时自动创建
  settings.json             # 平台凭证配置（文件权限 0600）
  reviews/
    <reviewId>/
      record.json           # 元数据、状态、整体结论、问题清单、失败原因
      diff.patch            # 本次审核的变更内容原文
```

无数据库，`DB_PATH` 等数据库配置不适用。审核记录以目录为单位，删除记录即删除该目录；列表接口只读取各目录的 `record.json` 摘要字段，不加载 `diff.patch`。

### 3.2 记录结构与状态

- 记录字段：`id`、`source`（`paste` / `mr-link`，链接方式附带平台、仓库、合并请求编号与原始链接）、`createdAt`、`startedAt`、`finishedAt`、`status`（`running` / `succeeded` / `failed`）、`attempts`（发起次数）、`changeSummary`（涉及文件数、增删行数）、`conclusion`（问题总数、是否存在高严重级问题）、`findings[]`、`failure`（`code` + `message`）。
- 单次审核在同一记录内只有一份当前结果；重新发起保留 `attempts` 递增，失败历史以 `failure` 覆盖为「最近一次失败原因」，界面展示当前状态与当前结果。
- 状态迁移只由队列执行：`running → succeeded`（写入结论与问题清单）或 `running → failed`（写入失败原因）；不允许跳过 `running` 直接写入结果。
- 服务启动时扫描 `status = running` 的记录，标记为 `failed`，失败原因为「服务重启导致审核中断，可重新发起」，避免遗留永久进行中的记录。

### 3.3 一致性与写入方式

- 每次写入先写同目录临时文件，再原子重命名覆盖目标文件，保证读取方不会看到半份内容。
- 同一进程内所有记录写入经由按记录串行的写队列，避免同一记录的并发更新互相覆盖；列表读取不加锁。
- 删除与重试并发时，删除优先：重试写入时不存在的记录直接丢弃并返回记录不存在，不重建目录。

### 3.4 凭证存储边界

平台凭证存于 `data/settings.json`，写入时文件权限设为 0600，读取接口只返回平台类型、实例地址、是否已配置与更新时间，永不回传令牌原文。令牌仅在服务端拉取合并请求时使用，不写入日志、不进入审核请求体、不随记录持久化。加密密钥管理不在本版本范围，凭证依赖本机文件权限保护，作为残余风险记录。

## 4. 外部集成

### 4.1 代码托管平台变更拉取

- 适配器注册表按配置的 `platform` 选择实现，当前支持 `github` 与 `gitlab`，实例地址可指向官方域或自建实例。
- 链接解析：从 MR 链接解析平台、仓库路径与合并请求编号；链接主机与已配置实例地址不匹配时按不支持处理，不隐式访问其它主机。
- GitHub：读取合并请求元数据（变更文件数、增删行数）后按 diff 媒体类型获取补丁文本。GitLab：读取合并请求变更列表，按文件拼接为统一 diff 文本，并汇总增删行数。
- 拉取为同步步骤，发生在创建记录之前：网络失败、凭证缺失或失效、链接无效、无权访问都直接返回对应错误码与可读原因，不创建记录、不产生空记录。
- 请求超时默认 20 秒；超时按网络不可用返回，并提示用户稍后重试。

### 4.2 AI 审核服务

- 使用 OpenAI 兼容的 `/chat/completions` 接口，服务地址、密钥与模型名由服务端环境变量提供（`AI_BASE_URL`、`AI_API_KEY`、`AI_MODEL`、`AI_TIMEOUT_MS`）。模型服务凭证属于部署配置，不在产品界面配置，避免扩展需求未提出的账号能力。
- 审核请求包含固定的审核指令与待审 diff，要求模型按严格 JSON 输出问题清单；服务端校验每个条目的文件、位置、级别、说明与建议，级别限定为高/中/低。输出无法解析时进行一次修补重试，仍失败则记录失败，失败原因为结果不可解析。
- 规模上限：diff 超过 400000 字符时不调用模型，直接按失败处理并说明超出可处理范围，用户可拆分后重新发起。
- 未配置模型服务时，审核以失败结束并给出「审核服务未配置」的明确原因，不产生伪造结果。
- 失败可见性：所有外部失败都落到记录的 `failure.code` 与可读 `message`，界面在记录详情中展示原因并提供重新发起入口。

### 4.3 外部调用的可替换性

审核引擎与平台适配器都以显式接口注入，`REVIEW_ENGINE`、`PLATFORM_FETCH_MODE` 只控制实现选择；接口签名一致，便于测试与后续扩展平台。

## 5. 运行与验证

### 5.1 启动与命令

| 场景 | 命令 | 说明 |
| --- | --- | --- |
| 安装依赖 | `npm install` | 单仓多包依赖统一安装 |
| 开发前端 | `npm run dev:web` | Vite 开发服务器，`/api` 代理到 `PORT` |
| 开发服务端 | `npm run dev:server` | 直接运行 `src/server.js`，支持热重启 |
| 构建前端 | `npm run build` | 输出 `dist/`，由服务端静态托管 |
| 常规启动 | `npm start` | 运行 `src/server.js`，托管 `dist/` 与 `/api` |
| 验收脚本 | `npm run verify` | 自行启动与清理服务，不额外后台启动服务 |

- 监听端口：`PORT`，默认 `8787`；验收脚本选择空闲端口并通过 `PORT` 传入。
- 数据目录：`DATA_DIR`，默认 `./data`；打开前创建目录及其父目录，干净目录无需人工准备即可启动。
- 本机数据隔离：验收脚本使用临时 `DATA_DIR`，结束后只清理本次启动的进程与临时目录。
- 审核与拉取的外部配置通过启动命令环境变量提供（`AI_*`、平台凭证在界面配置），未配置时按失败原因可见处理而非静默降级。

### 5.2 验收对应关系

- AC-01、AC-03：`REVIEW_ENGINE=stub` 生成确定性多级别问题，验证粘贴提交、状态推进、清单定位、级别筛选与按文件聚合。
- AC-02：`PLATFORM_FETCH_MODE=stub` 分别返回固定 diff 与 `unauthorized` / `not-found` / `network`，验证拉取成功产出清单，以及失败时无记录、原因可见。
- AC-04：`REVIEW_STEP_DELAY_MS` 保持进行中状态，结合 stub 引擎注入失败场景，验证失败原因展示与同一记录重新发起。
- AC-05、AC-06：临时 `DATA_DIR` 下完成审核后回看、删除并确认列表消失；全流程无登录步骤，凭证配置仅用于平台拉取。
- 界面验收在已启动的前端地址上进行；接口验收由 `npm run verify` 覆盖。

## 6. 架构决策

| 决策 | 选择 | 理由与影响 |
| --- | --- | --- |
| 持久化方式 | 本机文件存储，不使用 SQLite/dbkit | 数据为单用户本机记录，无跨用户共享、关联查询或事务需求；避免原生依赖与迁移机制。代价是列表需读取多份小文件，单用户规模下可接受；dbkit 已作为 SQLite 候选核查过，本次未选用 |
| 审核执行载体 | 单进程内串行队列 | 需求要求进行中可离开页面，属进程内后台推进即可满足；串行避免模型与平台限流。代价是进程重启会中断，已由启动恢复策略转为可见失败 |
| 服务端入口语言 | 服务端 ESM JavaScript，前端 TypeScript | 服务端免编译直接 `node src/server.js` 启动，减少构建环节；接口类型由前端声明与契约文档保证一致 |
| AI 服务配置位置 | 服务端环境变量 | 需求只要求配置代码托管平台凭证，模型凭证属部署配置；避免扩展到账号/多模型管理能力 |
| 凭证保护 | 0600 文件权限 + 接口脱敏 | 满足「凭证属本机数据、不对外共享」的可观察要求；未引入密钥管理体系，作为残余风险 |
| 链接拉取时机 | 创建记录前同步拉取 | 满足「拉取失败不产生空记录」，失败原因可直接在表单回显；代价是请求耗时较长，由超时与提示覆盖 |
